# 第 25 课：七题纠错、可信分组查询与贡献拆解

## 1. 本课解决什么问题

一句话：先用真实模型找出旧链路的错误，再用同一份公开 Excel 建一个可核对分组的新数据副本，让 Query 回答多指标与日期范围，让 Analysis 说明哪些分组贡献了变化。

这次把计划中的第 1～4 项作为一个功能包交付。用户仍从同一个 `taobao-agent` 命令和同一张 LangGraph 图进入；没有新造一个独立 Agent。**原文要求**是 Intent、Supervisor、Query、Analysis 的分工，以及 SQL Validator Gate 和可评估的业务答案。**必要工程补充**是使用 UCI 公开数据替代拿不到的淘宝业务库。国家和商品编码只是 UCI 真正提供的维度；它没有支付、补贴、访客和行业字段。

## 2. 它在整个 Agent 中的位置

旧数据库继续处理第 24 课七题：`Intent → Supervisor → Query（受控工具循环）→ 按需 Analysis`。新数据库走同一张图，Query 收集多指标、范围或分组证据；若用户问两天的分组变化，再交给 Analysis。`Supervisor.next_expert=analysis` 表示最终回答由 Analysis 负责，Query 仍先取数。

当前只需理解 LangGraph 的两个概念：**State** 是节点之间传递数据的字典；**条件边**根据 State 中是否已有完整证据，决定进入 Analysis 还是结束。本课没有增加图节点。

## 3. 修改了哪些文件

| 文件 | 本课关键入口 | 用途 |
| --- | --- | --- |
| `uci_analytics.py`、增强版指标 JSON | `import_uci_enriched()`、`query_uci_aggregate()`、`source_catalog()` | 从 Excel 新建数据副本，批准三个指标和两个维度；执行只读聚合。 |
| `metric_sql.py` | `build_aggregate_query()`、`validate_aggregate_query()` | 构造固定 `SELECT SUM` 模板，执行前核对完整 SQL、参数和实际字段。 |
| `intent_agent.py` | `IntentResult.metric_names/date_range`、`run_intent_once()` | 表达多指标与连续日期范围；修复在线评测发现的分类提示不清楚。 |
| `aggregate_agent.py` | `fetch_aggregate_evidence()`、`answer_group_analysis()` | Query 收齐证据后，Analysis 计算分组增减及其对总变化的贡献。 |
| `workflow.py` | `query_node()`、`analysis_node()` | 同一张图按数据源交接新的证据。 |
| `evaluation.py`、两份题集 | `score_case()`、`evaluate_dataset()` | 支持只跑指定题、查看诊断输出；另加增强版业务题。 |
| `tests/test_uci_analytics.py`、`tests/test_evaluation.py` | 业务断言 | 核对来源、合计、SQL 门禁、贡献计算和评测格式。 |

## 4. 调用链与数据怎么传

以“2010-12-02 交易明细金额比 2010-12-01 为什么下降？按国家拆解”为例：

1. `run_intent_once()` 请求模型，得到 `IntentResult`：主意图 `attribution`、指标、两个日期、维度 `国家`。`intent_node` 把它写入 `State.intent`。
2. `supervisor_node()` 选择最终专家 `analysis`，但先路由 `query_node()`。
3. Query 的 `fetch_aggregate_evidence()` 核对指标名、两个日期和维度；分别调用 `query_uci_aggregate()`。每次查询前，`validate_aggregate_query()` 对照已批准模板、绑定参数与真实 SQLite 字段。两天都成功后，结果一起放进 `State.aggregate_evidence`。
4. 条件边看到完整证据，进入 `analysis_node()`。`answer_group_analysis()` 只读取证据，不直接访问数据库。它对每个国家计算 `当日值－基期值`，检查各组差额之和等于总体差额，再写 `State.answer`。
5. `WorkflowResult.answer` 返回给命令行。数值来自只读数据库；模型不能提供原始 SQL、数据库路径或编造分组金额。

多指标范围查询也由 Query 完成。`IntentResult.metric_names` 是指标列表，`date_range` 是开始/结束日期；Query 对每个指标执行已批准的聚合。单日老问题仍沿原来的逐日 Tool Calling 路径走旧数据库。增强版里任务已由结构化参数完整指定，当前用确定性 Python 顺序执行，不再让模型重复选择相同的固定查询。这个取舍减少不必要的模型调用；第十章的要点是：**Tool Calling 适合让模型选择下一步，明确且固定的操作直接调本地函数更简单**。

## 5. 关键代码为什么这样执行

- **新数据库而不是改旧表**：原 `online_retail.sqlite` 只有日期、行类型、金额；本课新建 `online_retail_enriched.sqlite`，保留国家、商品编码、件数和行数。导入器拒绝已有目标文件，既不会覆盖旧数据，也不会把 CustomerID 写进新库。
- **三个指标有不同口径**：交易明细金额是正向行的 `line_amount_pence` 之和；正向商品件数是 `quantity` 之和；正向交易行数是每条正向明细的 `line_count=1` 之和。一行不是一笔订单；三者都不是支付指标。
- **SQL 仍由程序批准**：模型只提取指标和维度。程序把“国家”映射为 `country`、“商品编码”映射为 `stock_code`；日期和 `record_type=positive` 用参数绑定。`validate_aggregate_query()` 比对完整模板，改成 `MAX`、偷换日期、使用客户字段都会被拒绝。
- **贡献不是原因**：比如 A 国家减少 10 英镑，B 国家增加 5 英镑，总额只下降 5 英镑，则 A 对“净降幅”的数值贡献是 200%。它说明不同组互相抵消，不证明 A 国家导致下降。要解释经营原因，需要访客、转化、价格、补贴等额外证据。

## 6. 主要替代方案与选择

可以直接在旧 SQLite 上 `ALTER TABLE`，但那会改变已验证的七题数据源，也可能覆盖或破坏现有数据，所以选择新建副本。可以让 LLM 自由生成分组 SQL，但目前只有三项已批准指标和两种维度，固定模板更容易审核、测试和排查。可以引入 RAG 寻找口径，但三条规则已经是明确的本地定义；第 5 个功能包再根据知识规模引入按需检索。

## 7. 实际验证与完整纠错过程

### 第一步：七题真实模型首跑

在有 Plus Key 的终端运行 `TAOBAO_UCI_DB_PATH=data/uci_online_retail/online_retail.sqlite DASHSCOPE_API_KEY="$DASHSCOPE_PLUS_API_KEY" DASHSCOPE_MODEL=qwen-plus uv run taobao-eval`。**目的**：看真实模型是否完成当前已支持的七种业务问法；**实际**：4/7 通过，三题失败。它不能证明整个 Agent 的成功率。

| 失败题 | 真实观察 | 错误发生的位置 |
| --- | --- | --- |
| 三日最高/最低 | 模型输出 `data_query`，Query 只列三天金额，没有给最高/最低。 | Intent 把比较排序当成普通取数，Supervisor 因而没有进入 Analysis。 |
| 指标口径 | 模型输出 `table_meta`，但 `metric_name=null`，Query 要求补指标名。 | 意图类别对了，结构化参数漏了。 |
| 口径＋单日金额 | 模型只输出 `data_query`，返回金额，没回答计算口径。 | 第二任务没有进入 `secondary_intents`。 |

### 第二步：只重跑失败题取诊断证据

`taobao-eval --case ... --diagnostic` 只运行这三题，报告实际意图、指标、日期、维度和答案；诊断时 0/3 通过，并确认了上表的具体输出。这个开关只用于公开业务题的排错，默认评测报告不包含实际答案；异常仍只记录类型，不写内部详情或 Key。

### 第三步：改分类说明，不改计算

`run_intent_once()` 的系统提示新增三条通用规则：比较、最高最低、最大下降属于 `attribution`；表字段和计算口径问题仍必须提取指标名；同题既问口径又问日期数值必须保留两个意图。没有按题目 ID 写死分支，也没有让 Query 猜测缺失字段。

### 第四步：定向复测与完整回归

同三题定向复测为 **3/3**：最高/最低进入 Analysis，口径题有指标名，组合题同时输出 `table_meta` 和 `data_query`。随后运行完整七题 `taobao-eval --diagnostic`：**7/7 通过**，每题的意图、专家、指标、日期、维度和答案事实检查均为 `true`。完整回归是必要的，因为提示词修改可能影响原先通过的四题；这次 7/7 也只是一轮固定题集结果，不代表长期准确率。

### 第五步：新数据与安全验证

运行 `uv run taobao-import-uci-enriched 'data/uci_online_retail/Online Retail.xlsx' data/uci_online_retail/online_retail_enriched.sqlite`：成功新建数据库，Excel SHA-256 为 `43465a06f2ccf7c8b5bd2892bc7defb52f97487934fe93b16ae4c3936424676d`，正向 530104 行、取消 9288 行、其他 2517 行；日期覆盖 2010-12-01 至 2011-12-09。**目的**：获得分组字段；**不能证明**模型会正确识别所有自然语言问题。

运行 `UV_CACHE_DIR=/private/tmp/taobao-uv-cache uv run --locked --offline python -m unittest discover -s tests -p 'test_*.py' -q`：加入下述日期契约回归后，**96 个本地测试通过**，包括旧路径回归、SQL 篡改拒绝、不同国家的抵消贡献，以及增强版题集的多指标与日期范围评分。独立逐行扫描原 Excel，核对 2010-12-01/02 的三个指标及国家分组，全部与新 SQLite 一致。两日合计：交易明细金额 106709.17 英镑、正向商品件数 58248 件、正向交易行数 5135 行；每项国家分组合计等于总值。旧 SQLite 仍可查到 2010-12-01 的 58960.79 英镑。

**边界**：UCI 没有支付、补贴、访客数据，不能给出淘宝式完整归因。十道固定题各成功一轮，也不是长期准确率或任意问法的保证。

### 第六步：增强版三题在线首跑

用独立增强版库和 `scripts/eval/datasets/enriched.json` 运行真实模型评测：**2/3 通过**。国家贡献题与商品编码分组题均给出核验过的金额/件数；“多指标＋日期范围＋国家分组”在 Intent 结果校验时抛出 `ValidationError`，因此 Query 尚未执行。这个失败不能归因于 SQL 或数据库。

### 第七步：定位日期契约冲突并修复

只重跑失败题并打开安全诊断字段，仍为 **0/1**；`error_fields` 指出 `date_range and dates cannot be used together`。这说明模型同时返回了范围与日期列表。旧校验只要两者同时出现就报错，即使首尾日期一致，因而把可用参数挡在 Query 之前。这和 SQL 门禁无关，也不能靠重试数据库解决。

修改 `IntentResult.check_secondary_intents()`：`dates` 若为空，继续按范围查询；若非空，必须升序且首尾等于 `date_range.start/end`。对相互矛盾的日期仍抛错，避免 Query 按错误范围取数。系统提示优先要求范围问题只填写 `date_range`，但代码也接受一致的冗余表示，因为模型未必每次严格遵循提示。新增测试同时验证一致输入通过、越界和逆序输入被拒绝；完整本地测试为 **96/96**。

用相同的模型、数据库、问题再次只跑失败题，结果 **1/1 通过**。实际 Intent 同时返回 `dates=[2010-12-01, 2010-12-02]` 和 `date_range={start:2010-12-01,end:2010-12-02}`；两者一致，Query 返回金额 **106709.17 英镑**、件数 **58248 件**、行数 **5135 行**及国家分组。证明这一问法已从校验层走到数据库查询与答案层。

### 第八步：增强版完整回归

在增强版 SQLite 上运行 `taobao-eval --dataset scripts/eval/datasets/enriched.json --diagnostic`：**3/3 通过**。三题分别验证“多指标＋范围＋国家”、“两日国家贡献”和“商品编码件数”；每题的意图、专家、指标、日期、维度和答案关键词检查均为 `true`。这是一次真实 `qwen-plus` 运行，和本地 96 项测试互补；固定三题仍不足以估计真实用户问法的成功率。旧库七题完整回归仍是 **7/7**，两套题分别使用各自的数据源。

## 8. 本课相关知识

- 第九章上下文工程：Intent 的系统提示是分类规则进入模型上下文的位置。本课从实际失败回推哪条规则缺失，再用定向评测验证；没有为学习概念另建 ContextBuilder。
- 第十章通信：旧路径用 Tool Calling 让模型提出工具调用，新增强路径由 Query 按已核准任务直接调用 Python 函数。两条路径都会在数据库边界经过 SQL 校验；同进程专家交接不需要 MCP 或 A2A。
- 第十二章评估：本地单元/集成测试证明数据契约和安全边界；七题/增强版 Golden Dataset 看真实模型业务行为；本课没有 LLM Judge 或外部基准。失败要先定位 Intent、路由、查询、答案哪一层，再改动。

## 9. Agent 岗位面试知识点

以下是常见技术讨论点和模拟题，并非真实公开面经：

1. **为什么分组贡献不能叫因果归因？** 差额分解是恒等式，只告诉我们哪个组的观测值增减；营销、库存、季节等原因需要额外证据或实验。
2. **为什么 SQL 校验要放在数据库入口？** 上游模型、工具参数和候选 SQL 都可能出错；执行前再核对完整 SQL、参数、表字段，避免把“模型保证安全”当权限边界。
3. **怎么修 Agent 的真实模型错误？** 先保存逐题失败证据，再定位具体层，做最小改动；定向复测后还要跑全题回归，避免提示词修一题坏另一题。

## 10. 下一功能包前置条件
