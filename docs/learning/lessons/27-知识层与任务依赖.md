# 第 27 课：知识层与任务依赖

## 1. 这课解决什么问题

**一句话**：指标、规则、可用维度和 SQL 形状有了明确的知识来源；Supervisor 能把“查口径＋取数＋分析”拆成有依赖的任务，Query 不再只照固定的四工具顺序行动。

此前三任务问法会被 `plan_tasks()` 拒绝；Query 的每一步工具名都由程序指定。现在代码仍有安全顺序：必须先找到指标，知识齐备才构建 SQL，构建后才执行。但规则、片段和分组能力检索可由模型在当前允许范围内选择顺序。

**原文要求**：MDL 语义层、指标注册、规则/SQL 片段检索和 Supervisor 语义计划。**必要工程补充**：用本地、受校验的 JSON 建最小知识层；当前不是 WrenAI/TisPlus3 的生产服务。**用户要求**：保留必要的顺序限制，不让 Query 的 LLM 只机械重复固定四步。

## 2. 在整体图中的位置

```text
用户问题 → IntentResult
         → Supervisor：任务闭包 table_meta → data_query → analysis
         → Query：指标注册表 + MDL/规则/片段 → SQL Gate → SQLite → QueryEvidence
         → Analysis：从 QueryEvidence 计算变化；合并口径说明
```

LangGraph 的节点数未变。`State.task_plan` 是要完成的任务；`State.query_evidence` 是给 Analysis 的已核实数据；`State.metric_metadata` 暂存口径说明，避免三任务回答时丢失。

## 4. 用一个问题看参数和数据流

问题：“GMV 口径是什么？比较 2026-10-21 和 2026-10-22 并分析下降”。

1. Intent 输出主意图和次要意图，合起来包含 `table_meta`、`data_query`、`attribution`，日期和指标也在 `IntentResult` 中。
2. Supervisor 将 `attribution` 的前置任务 `data_query` 补入计划，并按依赖排成 `table_meta → data_query → analysis`。复杂组合时 LLM 可以提议计划；程序核对任务是否遗漏、重复或加入未批准任务，失败时回退到规则计划。
3. Query 从 `commerce_metrics.json` 找指标，用 `commerce_knowledge.json` 核对表、维度、筛选规则和 SQL 片段。模型可在 `rule_search`、`snippet_search`、按行业时的 `cap_search` 之间选择顺序；未满足依赖不能 `build_sql`。
4. SQL 片段渲染成候选 SQL 后，先与程序批准的固定 SQL 形状完全比较；到 SQLite 入口还会经过原有 SQL Validator Gate 核对真实字段和绑定参数。
5. Query 将口径说明写到 `State.metric_metadata`，数值写到 `State.query_evidence`；Analysis 只读证据计算，最终答案合并口径与分析。用户没有被要求分别提三次问题。

## 5. 为什么这么设计

指标注册表回答“有哪些已批准指标”，MDL 回答“表有哪些字段和维度”，规则回答“哪些行能计入”，片段回答“这一类查询使用什么 SQL 形状”。它们职责不同，但装入时互相核对；任一文件与口径矛盾，工作流在查询前拒绝启动。

Query 的模型现在有**受限的选择空间**，而非任意执行权限。对当前唯一表和两个 SQL 形状，模型能选的仍不多；以后知识和工具增加，选择的业务意义会更明显。若必须调用的步骤没有选择价值，继续交给确定性 Python。SQL Gate 永远不由模型替代。

Supervisor 的规则计划是任务依赖的闭包，不是完整 Plan-and-Execute。LLM 只在复合任务上提议已知任务，程序验证后使用；简单取数仍用规则。它不能凭空添加数据库权限或新专家。

## 6. 实际验证与限制

运行 `PYTHONPYCACHEPREFIX=/private/tmp/taobao-pycache .venv/bin/python -m unittest discover -s tests -q`：**32 项离线测试通过**。其中新增测试证明三任务两种主意图顺序均进入 Query→Analysis，结果保留口径和下降金额；Query 的知识检索顺序可不同；篡改 SQL 片段或规则会在加载时被拒绝。此命令的目的是验证代码和固定模型输出，**不能证明真实 Qwen 对新工具选择已稳定**。本课尚未进行在线模型回归。

当前知识层仅覆盖一张合成表、三项指标、一个维度和两种 SQL 形状；不是完整 WrenAI MDL，也没有向量检索。检索采取小数据规模下可解释的精确匹配，不为了演示 RAG 引入额外服务。

## 7. 对应的学习知识

- **第九章上下文工程**：Query 只在当前任务需要时取规则、片段和表能力，而非把整个知识文件塞进模型输入。
- **第十章通信协议**：本课工具是进程内 Python Tool Calling；Supervisor 与专家仍通过 LangGraph State 交接，无 MCP/A2A 需求。
- **第十二章评估**：分别测试计划是否漏任务、知识是否冲突、SQL 是否仍经过门禁，以及回答是否保留三项要求。固定模型测试和真实模型评测须分开报告。

## 8. Agent 面试知识点

以下是常见技术问题，不是公开真实面经：

1. 为什么把指标、MDL、规则、SQL 片段分开？它们分别约束业务名词、表能力、过滤口径和查询形状，便于逐层核对。
2. 为什么工具“可选”仍要有限制？模型可以决定检索顺序，但执行 SQL 必须满足已批准指标、规则、片段和 SQL Gate。
3. 为什么 `task_plan` 不等于完整 Plan-and-Execute？当前只处理已知任务及依赖，没有开放式重规划和任意子任务执行。
