# 第 34 课：专家工具与运行边界

## 1. 解决什么问题

面试时需要说清每个专家能做什么，以及谁可以访问数据库。现在工具的职责与权限有明确代码和执行记录。

## 2. 架构位置

`agents/` 下分别放 Intent、Supervisor、Query、Analysis、Ops、Other、Harness 和 SQL Gate。`tools/` 放专家实际调用的计算、任务读取、能力列表和 ETL。主图仍由 `workflow.py` 连接。

## 3. 本次文件与方法

- Query：六项已有工具；模型选择调用，程序验证顺序和参数。
- Analysis：`choose_view` 由模型选择视角，`funnel_reconcile` 和 `segment_contribution` 用确定性 Python 计算。
- Ops：`read_run()` 与 `read_run_logs()` 读取本机任务记录。
- Other：`list_capabilities()` 基于当前批准指标回答能力范围。
- Harness：`RunHarness.call()` 校验专家与动作的允许表，并记录成功、拒绝和失败。

## 4. 调用链与数据载体

Supervisor 选择专家 → 专家调用本职工具 → Harness 检查允许动作和预算 → 工具返回结构化值或文本 → 节点写入 `WorkflowState`。执行事件只记录 `run_id`、专家、动作、状态和耗时，不存问题全文或 Key。

## 5. 关键执行过程

Analysis 只拿 Query 已核实的数值，不能调用 `execute_query`；Ops 两个工具使用参数化 SQL 和只读连接；Other 的能力列表从指标目录加载。超时和暂时连接失败可重试一次，预算耗尽则停止。

## 6. 为什么这样设计

**原文要求**多专家工具和 Harness；当前采用**必要工程补充**的本地允许表。并非每个专家都必须让 LLM 自由调用工具：Query 是真正的 LLM Tool Calling，Analysis 由模型选分析视角，Ops/Other 当前用确定性分派。这样才能准确回答面试官“哪些是模型决策，哪些是程序约束”。

## 7. 测试与限制

最终 47 项离线测试通过，包含 Analysis 拒绝查询权限、工具轨迹、Ops 成败任务和日志。Harness 的同步超时是调用前后检查，不是能中断任意阻塞代码的进程沙箱；远程 DataWorks 运维不在范围内。

## 8. 相关知识

第十章：同进程工具调用不等于 MCP；MCP 在跨进程、跨服务统一暴露工具时才值得接入。第十二章：要分别评估工具选择、参数和执行。

## 9. 面试知识点

说出每个专家的工具、权限边界、失败处理与可观测性。这里给的是项目真实实现，不把模拟面试题说成公开面经。

## 10. 下一课前置条件

先理解执行事件与 `run_id`；第 35 课增加跨运行对话记忆，但历史回答不能成为新查询的事实来源。
