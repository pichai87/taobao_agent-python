# 第 10 课：把 GMV 口径写成可校验的规则

先看变化：第 9 课说“只加总已支付订单，按支付日期统计”，但指标文件没有这些信息。本课让 `examples/demo_metrics.json` 明确记录这条规则，并由现有加载流程检查它是否完整。Agent 仍不会查询数据库。

## 1. 本阶段解决的问题

只有 `table=demo_orders` 和 `field=order_amount_fen`，程序无法判断该求和、按哪天统计、要排除哪些订单。人能从第 9 课文字理解，后续查询程序却不能可靠地依赖口头约定。本课增加一份结构化的最小计算规则。

## 2. 在整体架构中的位置

```text
指标 JSON → load_metric_catalog() → MetricDefinition.calculation
                                        ↓
                                未来的 SQL 构建与校验

当前主图：用户问题 → Intent → Supervisor → Query → 查到指标并告知尚未取数
```

`calculation` 属于 Query 将来要使用的知识输入。本课没有增加 LangGraph 节点或边，也没有把整份指标文件放进 `WorkflowState`。原文要求指标语义和 SQL Validator Gate；此处的 JSON 结构是**必要工程补充**，并非原文指定的完整 MDL 或规则库。

## 4. 调用链、参数、State 和返回值

主命令设置 `TAOBAO_METRIC_CATALOG_PATH` 后，`main()` 把文件路径交给 `load_metric_catalog()`。Pydantic 将 JSON 的列表转换为 `tuple[MetricDefinition, ...]`；每个指标的 `calculation` 若存在，会继续转换为 `MetricCalculation`，其中的 `condition` 转为 `EqualsCondition`。缺少必需字段或出现额外字段时，加载器抛出 `ValueError`，主命令以配置错误退出，**此时还没有创建模型或发请求**。

合法目录仍由 `run_workflow(..., metric_catalog=...)` 传给 Query 节点。当前 `answer_query()` 只查指标名并报告表和字段；它尚未读取 `calculation`。`WorkflowState` 仍只在节点之间传递问题、意图、专家选择和回答。

## 5. 关键代码怎样执行

样例指标现在除了原来的四项，还包括：

```json
"calculation": {
  "aggregation": "sum",
  "date_field": "paid_date",
  "condition": {"field": "payment_status", "value": "paid"},
  "unit": "fen"
}
```

把它读成一句话：按 `paid_date` 归属日期，只取 `payment_status` 等于 `paid` 的订单，把外层 `field=order_amount_fen` 求和，结果单位是“分”。`aggregation` 当前只允许 `sum`；`condition` 当前只表达**一个等于条件**。Pydantic 会拒绝 `average`、空字段、缺少日期字段或偷偷加入原始 `sql` 键。

旧的四字段指标文件可以继续加载，得到 `calculation=None`。这表示只有“指标在哪里”，还没有完整计算规则，不能用它自动取数。样例测试还检查 `field`、`date_field`、条件字段确实存在于**这张合成表**；当前运行时不会连接用户的数据库核实字段。

## 6. 为什么这样设计，替代方案是什么

- **原文要求**：先找到指标、表字段和业务规则，SQL 执行前通过校验。
- **必要工程补充**：把本项目已明确的 GMV 口径写成小型结构化对象，让缺项尽早报错；不要求用户现在提供真实 MDL。
- **替代方案**：在 JSON 里直接写一整段 SQL，或让模型从文字规则临时生成过滤条件。当前缺少字段权限与 SQL Gate，因此本课只保存数据项，保留后续逐项验证的机会。

格式校验只证明规则长得符合预期。它不能证明表是可信来源、字段存在于真实库、`paid` 是真实状态值、金额单位准确，或 SQL 执行安全。

## 7. 实际运行验证与已知限制

在项目根目录执行：

```bash
UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -v
```

目的：同时验证新规则、旧四字段目录、合成表映射和现有工作流。实际 **36 个测试通过，退出码 0**。其中包含非法聚合、缺日期、空条件字段、额外 `sql` 键，以及主命令在无效规则下不创建模型的测试。它们是本地单元与集成测试，不能证明真实模型输出或真实数据库结果。

执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv sync --locked --offline`：解析 45 个包、检查 44 个已安装包，退出码 0；没有新依赖。执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline taobao-agent --help`：退出码 0，只证明入口可启动。本课未使用 API Key 进行在线调用，也未执行 Agent 生成的 SQL。

**软件提醒**：本课及样例测试只用 Python 标准库 `sqlite3` 的内存数据库，**不需要安装 MySQL、PostgreSQL、Navicat 或其他数据库软件**。以后若确实要接外部数据库，会先在相应课程文档说明所需软件、版本、用途和安装方法。Navicat 是可选的图形查看工具，并非运行 Agent 的前提。

## 8. 本课关联的知识

- **LangGraph**：没有新图 API。计算规则是传给 Query 的外部知识，尚未写入 State。
- **第九章，上下文工程**：把业务事实保存在可追溯的指标文件里，只在相关专家需要时读取；提示词不能代替经校验的业务口径。
- **第十章，通信协议**：这里是文件读取与本地对象校验，没有 MCP、A2A 或远程工具调用。
- **第十二章，评估**：测试既要有合法样例，也要有明确的错误样例。规则合法性、业务正确性与真实 Agent 成功率需要分别验证。

## 9. Agent 岗位面试知识点

这是**常见技术知识点与模拟题**，不是公开面经：“为什么 NL2SQL 前要有指标语义层？”可以用本课说明：用户只说“GMV”，数据库字段不能告诉程序聚合方法、日期归属和订单过滤条件。结构化语义层使这些选择可见、可测；SQL Gate 还要独立验证生成语句及权限。

## 10. 下一阶段前置条件

能读懂 `calculation` 中每一项怎样对应第 9 课的 200 元计算。下一课若构建 SQL，只允许当前已支持的结构化字段，先核实表字段与只读边界，再执行合成数据查询。公开数据与真实业务库接入仍需另行核对数据许可、表结构和指标口径。
