# 第 9 课：建立可核算的教学数据

先看结论：我们现在有一张**自己编造的小订单表**，能用固定 SQL 算出三个日期的 GMV。它为后续开发提供已知正确答案。本课不让 Agent 查询数据库；主命令的行为不变。

## 1. 本阶段解决的问题

第 8 课能从 JSON 查出“GMV 对应哪个表和字段”，但项目没有这张表，也不知道该如何过滤未付款订单。若直接让模型生成 SQL，得到的金额没有可核对的口径。本课先把一份很小的数据和计算约定定下来。

## 2. 在整体 Agent 架构中的位置

```text
本课：合成订单 SQL ──→ 内存 SQLite ──→ 固定 SQL 核算预期值
      指标 JSON ─────→ 现有 load_metric_catalog() 格式检查

未来：用户问题 → Intent → Supervisor → Query → 口径校验 → SQL Gate → 数据查询
```

上面第一行只在测试中执行，不在 LangGraph 图里。原文要求查询前有 MDL、指标与规则资料，并在执行 SQL 前经过 SQL Validator Gate。合成样例和 SQLite 是**必要的工程补充**，用于学习和测试；不是原文指定的数据源。

## 3. 修改的文件和关键内容

| 文件 | 本课作用 |
| --- | --- |
| `examples/demo_shop.sql` | 创建 `demo_orders` 表，插入 6 笔合成订单 |
| `examples/demo_metrics.json` | 使用第 8 课的四字段格式，标明 GMV 的表和金额字段 |

## 4. 调用链、参数、State 和返回值

测试打开 `sqlite3.connect(":memory:")`，读取并执行 `demo_shop.sql`，得到只在本次测试进程中存在的 `demo_orders`。然后运行固定的 `SELECT ... SUM(order_amount_fen) ... WHERE payment_status='paid' GROUP BY paid_date`，返回 `(日期, 分数金额)` 列表，测试与人工写定的预期列表比较。

另一个测试调用现有 `load_metric_catalog(Path(...))`，得到 `tuple[MetricDefinition, ...]`，检查 `table=demo_orders` 和 `field=order_amount_fen`。这份目录**没有**被自动传进正在运行的 Agent，也没有改变 `WorkflowState`。如果以后显式设置 `TAOBAO_METRIC_CATALOG_PATH`，现有 Query 只会报告找到定义，仍不会返回 GMV 数字。

## 5. 关键代码执行过程

每行是一笔订单；`order_amount_fen` 用整数“分”保存，避免小数金额的浮点误差。`paid_date` 是支付成功的自然日；未支付、已取消订单没有支付日期。表的 `CHECK` 约束会拒绝不匹配的状态与日期。

本课**演示口径**：GMV = 指定支付日期内、`payment_status='paid'` 的订单金额之和，不计未付款和已取消订单。2026-10-22 有两笔成功订单：12000 分 + 8000 分 = 20000 分，即 200 元。2026-10-21 是 30000 分，即 300 元。这个差值只能说明样例数字，不能说明真实业务下降原因。

注意：当前 JSON 只记录指标名、表、字段和来源，**尚未机器可读地记录 `SUM`、支付状态过滤与支付日期字段**。所以“查到 GMV 定义”还不等于“具备自动生成正确 SQL 的全部知识”。这正是下一课需要解决的缺口。

## 6. 设计原因与替代方案

- **原文要求**：业务查询依赖表字段、指标语义和规则；真正执行 SQL 前还要校验。
- **必要工程补充**：先用 6 笔标为合成的数据建立可重复的预期答案，且用 Python 自带的 SQLite 验证，不增加依赖，也不假装拥有淘宝数据。
- **公开数据候选**：[UCI Online Retail](https://archive.ics.uci.edu/dataset/352/online+retail) 有交易、数量、单价与取消标记，并注明 CC BY 4.0 许可；它没有本样例的支付状态字段，不能直接套用此处“已支付 GMV”口径。[Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) 包含多表电商记录，后续若采用，要先核对获取方式、许可、支付与订单状态口径。公开数据也没有淘宝百亿补贴的专属字段。
- **替代方案**：立即下载完整公开数据并导入数据库。当前连最小支付过滤规则都没有机器可读的定义，先用小样例把口径和测试确定下来，再接较大的数据更容易发现错误。

## 7. 实际测试结果和限制

在项目根目录执行：

```bash
UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -p 'test_demo_data.py' -v
```

目的：不使用 API Key，在内存数据库载入 6 笔订单，检查固定金额和指标文件。预期为 2 个测试通过、退出码 0；实际也是 **2 个测试通过、退出码 0**。这证明样例和固定 SQL 自洽，不能证明 Agent 会自动生成 SQL，也不能证明真实 GMV 口径。

另执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -v`：**34 个测试通过，退出码 0**。执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv sync --locked --offline`：解析 45 个包、检查 44 个已安装包，退出码 0；本课没有新增依赖。执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline taobao-agent --help`：退出码 0，只证明主命令入口可启动。

当前没有在线模型调用、真实公开数据导入、业务数据库、SQL Validator Gate 或 RAG。测试中的 SQL 是人工固定写出的，只用来做已知答案。

## 8. 相关知识

- **LangGraph**：本课不增加图概念。未来 Query 节点拿到完整指标契约后，才可调用查询工具。

- **第十二章，评估**：固定样例与预期数字是最小的业务测试集。它验证计算口径的一部分，与单元测试、在线 Agent 业务评测和外部基准各有范围。

## 9. Agent 岗位面试知识点

这是**常见技术知识点与模拟面试题**，并非公开面经：“有表名和金额字段，为什么还不能自动回答 GMV？”可以用本课解释：还缺聚合函数、支付状态条件、日期归属和单位；模型猜其中任何一个，都可能给出看似合理但错误的数值。工程上应让这些口径可查、可校验、可回归测试。

## 10. 下一阶段前置条件

能独立解释 200 元怎样从两笔订单算出，以及未支付、已取消订单为何不计入。下一课把这些文字口径整理成可校验的指标契约，然后才进入只读查询与 SQL Gate 的设计。公开数据导入前，还要确定具体数据集、许可与字段映射。
