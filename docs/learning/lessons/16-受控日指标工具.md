# 第 16 课：受控日指标工具

> 历史课程提示：第 17 课已移除运行时教学数据分支；本课关于 demo 工具与数据源二选一的描述仅记录当时实现。当前 `query_daily_metric` 只绑定 UCI 数据源。

## 1. 本课解决的问题

你问过：`fetch_comparison()` 最后是不是应该写成工具供 Query 调用？它现在负责安排“两次单日查询”，而单日回答又有另一处取数代码。我们需要一个清楚、可重复使用的**单日取数入口**。

一句话结论：**`query_daily_metric` 是受控取数工具；`fetch_comparison()` 是 Query 专家安排两次工具调用的流程。**

## 2. 在整体 Agent 架构中的位置

本课没有改变 LangGraph 图。单日问题仍走 `Intent → Supervisor → Query`；两日问题仍走 `Intent → Supervisor → Query → Analysis`。变化发生在 Query 节点内部：两条路径都通过同一个 `query_daily_metric` 工具取得某一天的金额。

原文要求 Query 使用工具完成查询，并在 SQL 执行前通过校验。本课属于**必要工程补充**：把已有的安全取数函数整理为一个参数范围很窄的 LangChain 工具接口。我们没有添加新的业务指标，也没有让 Query 的 LLM 自主选择工具。

## 4. 现在的调用链与数据流

单日问题：

```text
IntentResult(metric_name="交易明细金额", curr=2010-12-01)
  → Query.answer_query()
  → query_daily_metric.invoke({"metric_name": "交易明细金额",
                               "business_date": "2010-12-01"})
  → 已批准指标目录 → UCI 固定 SQL 门禁 → 只读 SQLite
  → DailyMetricValue(amount_minor=5896079, source="uci", unit="pence")
  → Query 格式化为 58960.79 英镑 → State.answer
```

两日问题：Query 的 `fetch_comparison()` 对 `prev` 和 `curr` 各调用一次上述工具；两次都成功后才构造 `QueryEvidence`，交给 Analysis。Analysis 不导入查询工具，也不接触数据库路径。

工具的**公开参数**只有 `metric_name` 和 `business_date`。指标目录、教学模式开关与 UCI 数据库路径在创建工具时由程序绑定；它们不出现在工具参数中。模型以后若获得这个工具，也不能通过工具参数提交任意数据库路径或 SQL。

## 5. 关键代码的执行过程

1. `make_daily_metric_tool()` 要求程序明确选择且只选择一个数据源：合成教学数据或 UCI 本地数据库。没有配置数据源时，Query 仍按原有规则说明不能取数。
2. `@tool` 将内部 Python 函数转换为 LangChain 工具。`DailyMetricInput` 限制工具参数为非空指标名和日期，额外字段会被拒绝。
3. 工具从已传入的指标目录查指标，并核对它与当前数据源的内置批准定义一致。随后调用原有的 `query_demo_metric()` 或 `query_uci_metric()`；固定 SQL 构建、Validator Gate 和只读执行仍在底层函数里。
4. 工具返回整数金额、日期、来源和单位。Query 用 `DailyMetricValue` 校验结果，并核对返回的指标和日期与请求一致，再决定是生成单日回答，还是把两次结果装进 `QueryEvidence`。
5. 任一次查询失败时，两日流程不会交出半份证据；错误说明仍不包含内部数据库路径。

本课没有新增 LangGraph 概念：它是在现有 Query 节点内部整理工具调用。

## 6. 为什么这样设计；其他做法

- `fetch_comparison()` 保持为 Query 专家的**协调函数**：它决定查 `prev` 和 `curr` 两次，属于任务流程；单日取数才是可以反复调用的工具能力。把整个比较流程都注册为工具，会把“专家如何安排步骤”和“工具提供什么能力”混在一起。
- 工具输入只暴露指标名和日期，避免把数据库路径、指标定义对象或原始 SQL 作为可调用参数。即使以后引入模型工具选择，数据源与业务规则仍由程序控制。
- 工具内再核对批准的指标定义，看起来与 Query 的预检查有重叠。Query 的检查用于及时给用户说明当前支持范围；工具必须独立守住执行边界，不能因为调用方已经检查过就信任任意输入。
- 直接继续调用两个普通 Python 函数也能工作，但单日与两日路径会各自处理数据源选择。现在用一个明确的工具契约，为下一步模型调用工具提供可验证的边界。

## 7. 实际验证和限制

在项目根目录运行：

```bash
UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -v
```

**目的**：验证工具参数白名单、拒绝未经批准指标、返回日期核对、单日与两日结果、错误处理及原有工作流。**实际结果**：72 个测试通过，退出码 0。**不能证明**：LLM 已能自主选工具，或所有自然语言问题都能正确取数。

还用假模型贯穿本机已有 UCI SQLite：节点顺序仍为 `intent、supervisor、query、analysis`；工具得到 5896079 与 4774838 便士，最终答案仍为下降 11212.41 英镑、19.02%。这验证真实本地数据和新工具链，**没有发在线模型请求**。

以下命令用于你在自己的终端复核主流程；若 Plus Key 仍在该终端环境变量中，无需重新输入：

```bash
env -u TAOBAO_METRIC_CATALOG_PATH -u TAOBAO_DEMO_DATA TAOBAO_UCI_DB_PATH=data/uci_online_retail/online_retail.sqlite DASHSCOPE_API_KEY="$DASHSCOPE_PLUS_API_KEY" DASHSCOPE_MODEL=qwen-plus uv run taobao-agent '2010-12-02 交易明细金额为什么比 2010-12-01 下降？'
```

**目的**：用一次真实模型调用检查新工具路径是否保持同样结果。**预期**：`next_expert=analysis`、下降 11212.41 英镑和变化率 19.02%。本课结束时尚未用用户 Key 再次运行；一次成功也不是 Agent 准确率。仍只需 Python 自带 SQLite，不需要安装数据库服务或 Navicat。

## 8. 与 Hello-Agents 的关系

- **第九章，上下文工程**：工具输入只接收本次查询必需的指标名和日期；数据源配置保留在程序侧，不需要塞给模型。
- **第十章，通信协议**：现在的 `.invoke()` 是**Python 程序主动调用 LangChain 工具**，不是 LLM Tool Calling。真正的 Tool Calling 还需要把工具绑定给模型、读取模型提出的工具调用、验证并执行，再把结果交回模型。当前不需要 MCP 或 A2A。
- **第十二章，评估**：除最终答案外，还测试工具的参数边界和未经批准指标不会访问底层数据库；这是本地测试，不是模型选择工具的准确率。

## 9. Agent 岗位面试知识点

常见技术知识点：**Tool Calling 与普通函数调用有什么区别？** 本课的 `.invoke()` 仍由程序写死调用时机和参数；模型没有作工具选择。以后接入模型时，要分别评估“选对工具”“参数正确”“工具执行正确”和“答案有证据”四件事。工具接口应尽量只开放业务所需参数，让权限边界不依赖模型自觉。这是项目工程实践，不是引用某份公开面经原题。
