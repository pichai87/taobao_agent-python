# 第 35 课：长对话记忆与上下文隔离

## 1. 解决什么问题

此前只保存上一轮指标和日期，问到第三轮时容易失去背景。现在同一会话可取最近三轮，再按本轮指标找一条较早相关记录。

## 2. 架构位置

LangGraph 的 SQLite checkpoint 保存图状态；`memory.py` 在同一文件里维护独立的 `conversation_turns` 表。Intent 节点读压缩过的历史，Query 仍要重新查库核对数值。

## 3. 本次文件与方法

- `memory.py`：`remember()` 写已完成问答与结构化槽位；`recall()` 按 `session_id` 读取、相关性筛选和字符预算截断。
- `workflow.py`：在图运行前取历史，在成功结束后保存；原有 `session_context` 继续支持“那前一天呢”。
- `agents/intent_agent.py`：历史只用于消解指代，提示词明确不把旧答案当证据。

## 4. 调用链与数据载体

`session_id` → `recall()` → `WorkflowState.conversation_context` → Intent 提示 → 新 `IntentResult` → Query → 新证据 → `WorkflowResult` → `remember()`。最近槽位仍以 `WorkflowState.session_context` JSON 保存。

## 5. 关键执行过程

历史最多扫描该会话最近 30 行，取最近三轮与至多一条更早的指标匹配；每轮文本和总字符数都有限制。不同 `session_id` 的 SQL 查询互不混用。取数失败没有完整证据时不保存为成功记忆。

## 6. 为什么这样设计

这是第九章上下文工程的**必要工程补充**：把 State、持久化记忆和模型输入区分开。没有把全部历史塞进提示词，也没有把历史回答送到 SQL 工具当作权威数据。向量记忆属于可选优化，当前数据量不值得引入。

## 7. 测试与限制

最终 47 项离线测试通过，覆盖三轮恢复、会话隔离、旧指标召回和字符上限。真实模型在长对话里是否正确理解指代尚未评测，留到第 37 课；目前没有自动摘要或冲突纠正。

## 8. 相关知识

区分 Messages（当轮输入）、State（图运行字段）、Context（送给模型的选定内容）和 Memory（跨运行保存的信息）。

## 9. 面试知识点

能解释记忆污染、上下文预算、会话隔离、检索相关性与“历史答案不得替代实时取数”。这是常见技术知识点。

## 10. 下一课前置条件

了解 `session_id` 与 checkpoint 的关系；第 36 课让 CLI 和 HTTP 复用同一工作流。
