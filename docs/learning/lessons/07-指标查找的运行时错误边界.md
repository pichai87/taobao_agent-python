# 第 7 课：指标查找失败时怎样安全结束

先看区别：Query 查不到 GMV 定义，会回答“尚未配置”；如果指标目录**超时或连接失败**，现在会回答“指标目录暂时不可用”。这两种情况不能混在一起，因为前者是资料缺失，后者是工具运行失败。

## 1. 本阶段解决的问题

第 6 课让 Query 调用 `search_metrics`。一旦将来指标目录接到外部服务，查找可能超时或断线。此前这类异常会沿 LangGraph 调用链冒出，使整个命令以异常结束。本课在工具调用处增加一个很小的 Harness 错误边界，让已知的运行故障得到清楚、有限的处理。

## 2. 在整体 Agent 架构中的位置

```text
Intent → Supervisor → Query → Harness → search_metrics
                          ↑             ↓
                          └── 查找结果或“工具不可用”
```

原文 PDF 第 7 页称 Harness 为防止 Agent 失控的“刹车系统”，第 22 页在项目结构中列出 `harness.py`。PDF 没有给出可核实的重试次数、超时阈值等具体参数。本课只实现现有工具路径上的故障边界；**没有实现完整 Harness，也没有 SQL Validator Gate**。后者须在出现实际 SQL 路径时接入。

## 3. 本次修改的文件、类和关键函数

| 文件 | 作用 |
| --- | --- |
| `src/taobao_agent/harness.py` | `guarded_metric_search()` 调用指标查找；遇到超时或连接失败时抛出统一的 `ToolUnavailableError` |
| `src/taobao_agent/query_agent.py` | Query 捕获 `ToolUnavailableError`，返回不含内部地址或异常详情的提示 |
| `tests/test_workflow.py` | 模拟超时、断线和程序错误，检查三者的不同处理 |
| README、本课、学习路线、学习记录 | 说明本次范围与实际验证 |

没有新增依赖或 LangGraph 节点。Query 仍是原来的 Query 节点。

## 4. 调用链、参数、State 和返回值

以“昨天 GMV 多少？”遇到指标目录超时为例：

```text
State.intent.metric_name="GMV"
  → Query 节点调用 answer_query(intent, catalog)
  → answer_query 调用 guarded_metric_search("GMV", catalog)
  → search_metrics 在查目录时抛出 TimeoutError
  → Harness 转为 ToolUnavailableError
  → Query 形成安全提示，写入 State.answer
  → WorkflowResult 输出 next_expert="query" 和 answer
```

`question`、`intent`、`next_expert` 的含义与前几课相同。本课没有新增 State 字段：已有的 `answer` 用于告知用户结果。正常查到指标、正常查不到指标时，仍按第 6 课的规则返回。

## 5. 关键代码的执行过程

Harness 只包住 `search_metrics()` 这一小段调用。它捕获 `TimeoutError` 和 `ConnectionError`，把两种已知运行故障统一为 `ToolUnavailableError`。Query 捕获这个异常后，给出“指标目录暂时不可用，请稍后重试。当前没有执行数据查询。”；底层异常中的服务地址等内容不会放入用户回答。

**程序写错**（例如 `ValueError`）不会被当成“目录暂时不可用”。它继续抛出，让开发者能发现并修正代码。这里没有自动重试，也没有计时器去主动中断慢函数；`TimeoutError` 必须由被调用工具或它的客户端抛出，Harness 才能处理。

## 6. 设计原因与主要替代方案

- **原文要求**：运行时安全守卫，以及后续 SQL Validator Gate。
- **必要工程补充**：当前有可执行的指标查找工具，因此先定义工具故障的处理边界；只捕获已知运行故障，避免掩盖程序错误。
- **替代方案**：在 Query 中直接写两种 `except` 也能工作。本课把错误分类放到 Harness，是为了在将来接入更多工具时复用同一位置的运行规则；目前它仍是一个很小的封装。

## 7. 实际测试结果和已知限制

在项目根目录执行：

```bash
UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -v
```

这条命令不需要 API Key，也不访问外部服务。**27 个测试通过，退出码 0**。新增测试模拟指标目录超时和连接失败，检查主流程仍能返回安全提示且不泄露模拟的内部地址；另一个测试证明 `ValueError` 仍会抛出。原有“找到指标”“指标不存在”、Other 和 Analysis 路径继续通过。

这些测试证明的是**模拟故障下的代码行为**。当前目录仍为空，还没有真实外部服务，因此没有验证真实网络超时、真正的重试或恢复；本课也没有执行 SQL。第 6 课的在线 Query 样例仍待用户终端验证，它不会触发本课模拟的故障。

另执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline taobao-agent --help`：退出码 0，主命令仍可启动；帮助输出不验证故障路径，故障行为由上面的模拟测试检查。

## 8. 本阶段涉及的相关知识

- **LangGraph**：没有新增 API；Query 节点仍通过返回 `{"answer": ...}` 更新 State。
- **第九章，上下文工程**：错误提示只包含用户需要知道的“暂时不可用”，不把底层异常详情放进对话上下文。将来可以把详细错误留在受控日志中，供调试使用。
- **第十章，通信协议**：现在的查找仍是本地 Python 函数。若以后目录由远程服务提供，连接故障会更常见，届时还要按实际协议与客户端决定超时和重试策略。
- **第十二章，评估**：这是失败路径的回归测试，检验故障分类和对外回复。它不同于 Agent 业务评测、LLM Judge 或外部标准基准。

## 9. Agent 岗位面试知识点

这是常见工程知识点，**不是公开面经**：为什么不能用 `except Exception` 把所有错误都变成“工具不可用”？因为那会掩盖程序缺陷，并误导用户以为只需重试。可以结合本项目说明三种结果：未找到指标是正常业务结果；超时/断线是可识别的运行故障；代码错误需要暴露给开发者修复。

## 10. 下一阶段的前置条件

先能解释 Query、Harness 和 `search_metrics` 各负责什么，以及为什么“未配置”和“暂时不可用”不同。要进入 SQL 安全校验，需要经过核验的指标/表/字段/业务过滤规则和一个真实的 SQL 构建路径；执行前还需明确只读权限边界。没有 SQL 时，编写一个无法接入当前流程的 SQL Validator Gate 不能证明系统安全。
