# 第 8 课：让 Query 读取外部指标定义

先看变化：第 6 课的 Query 已会查指标，但正式运行时目录始终为空。本课让主命令在启动时读取一个**可选的 JSON 指标文件**，把文件里的定义交给同一张 LangGraph 主图。当前没有真实文件时，运行行为保持原样。

## 1. 本阶段解决的问题

如果把“GMV 对应哪张表、哪个字段”写死在 Python 代码中，换数据源时必须改程序，而且难以看出定义来自哪里。本课把这份最小知识移到外部文件，并在调用模型前检查格式。它解决的是**知识从哪里进入 Query**；不负责证明知识本身正确。

## 2. 在整体 Agent 架构中的位置

```text
指标 JSON 文件（可选） → 加载与格式校验 → metric_catalog
                                          ↓
用户问题 → Intent → Supervisor → Query → search_metrics → 回复
```

原文 PDF 第 8–9 页的 `mdl.json` 描述表、字段等语义；第 16–17 页还有指标注册资料，用于公式与归因。本课的 JSON 只包含 `name`、`table`、`field`、`source` 四项，是**项目当前 Query 所需的最小过渡格式**，不是完整的 WrenAI MDL，也不是 RAG 知识库。

## 3. 本次修改的文件、类和关键函数

| 文件 | 作用 |
| --- | --- |
| `src/taobao_agent/metric_search.py` | `MetricDefinition` 改用 Pydantic 校验四个非空字段，拒绝多余字段 |
| `src/taobao_agent/metric_catalog.py` | `load_metric_catalog(path)` 读取 JSON，拒绝无效内容和重复指标名 |
| `src/taobao_agent/workflow.py` | 主命令读取 `TAOBAO_METRIC_CATALOG_PATH`；配置了路径就加载文件，然后把目录交给原有主图 |
| `tests/test_metric_catalog.py`、`tests/test_workflow.py` | 验证缺失文件、重复名称、无效格式，以及 CLI 到 Query 的完整数据传递 |
| README、本课、学习路线、学习记录 | 说明文件格式、运行目的与验证边界 |

没有新增依赖，也没有生成任何真实指标文件。

## 4. 调用链、参数、State 和返回值

```text
环境变量 TAOBAO_METRIC_CATALOG_PATH
  → main() 调用 load_metric_catalog(Path(...))
  → 得到 tuple[MetricDefinition, ...]
  → run_workflow(question, model, reference_date, metric_catalog)
  → Query 节点调用 answer_query(intent, metric_catalog)
  → search_metrics 查到定义或返回 None
  → State.answer → WorkflowResult.answer → CLI JSON
```

`metric_catalog` 是传给图的外部知识，不是 LangGraph State 中逐步写入的字段。Intent 仍只从问题提取 `metric_name`；它的 `metric_field` 仍为 `null`，不会让模型猜字段。Query 才从目录查表和字段。没有设置环境变量时，`metric_catalog=()`，所以会继续回答“尚未配置”。

## 5. 关键代码如何执行

文件顶层是一个 JSON 列表。以下只是**格式示例，表和字段都是虚构的，不能当作真实业务配置**：

```json
[
  {
    "name": "示例指标",
    "table": "demo_sales_daily",
    "field": "demo_amount",
    "source": "教学示例"
  }
]
```

`load_metric_catalog()` 先读文件，再让 Pydantic 检查每项是否有四个非空字符串、是否出现额外字段，最后检查名称忽略英文大小写后有无重复。文件不存在、内容无效或名称重复时，主命令以配置错误退出；这些检查发生在创建模型和发送请求之前。**格式合格不代表表、字段或指标口径已经由业务人员核实**。

## 6. 设计原因与主要替代方案

- **原文要求**：查询前应由语义资料提供表和字段；指标注册与 MDL 各有职责，知识需要审核后复用。
- **必要工程补充**：当前没有用户的真实 MDL 或数据库权限，先提供可注入、可校验的最小文件入口。默认空目录，避免把文章示例表误当成用户环境的真表。
- **替代方案**：可以直接接 WrenAI 或远程 RAG，但当前还没有真实 MDL、规则库和检索资料。先验证本地知识输入边界，后续再让这些资料替换或扩展这个入口。

## 7. 实际测试结果和已知限制

在项目根目录执行：

```bash
UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -v
```

这条命令不需要 API Key。**32 个测试通过，退出码 0**。新增测试用临时文件证明：有效目录可从 CLI 传到 Query；未设置路径时仍使用空目录；缺字段时在模型调用前退出；缺失文件和重复指标名被拒绝。测试文件中的表名是虚构的，不证明真实库中存在这些表。

另执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv sync --locked --offline`：解析 45 个包、检查 44 个已安装包，退出码 0；本课未增加依赖。执行 `UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline taobao-agent --help`：退出码 0。这两项只检查依赖环境与命令入口。

若日后你提供经核对的指标文件，可在**运行主命令的同一终端**设置：

```bash
export TAOBAO_METRIC_CATALOG_PATH=/实际路径/metrics.json
```

这条命令只指定文件位置，不发送模型请求。在已经准备 Plus Key 的同一终端，随后可运行 `DASHSCOPE_API_KEY="$DASHSCOPE_PLUS_API_KEY" DASHSCOPE_MODEL=qwen-plus uv run taobao-agent '昨天 GMV 多少？'`，才会加载文件并调用模型。当前项目没有真实指标文件，本次未做在线业务验证。即使文件加载成功，Query 仍只报告查到的定义，**不会执行 SQL 或返回 GMV 数值**。

## 8. 本阶段涉及的相关知识

- **LangGraph**：图的节点和边没有增加。外部指标目录在建图时传入，Query 需要时才查找；State 仍传递问题、意图、专家选择和回答。
- **第九章，上下文工程**：这是“按需提供上下文”的第一步。指标知识放在独立资料中，只有 Query 的查找函数使用；目前没有把整份目录塞进 LLM 提示词，也没有上下文压缩或记忆。
- **第十章，通信协议**：文件读取与本地函数调用都在同一进程，尚无 MCP、A2A 或远程 RAG 协议。
- **第十二章，评估**：本地测试验证格式和调用链。业务评测还需要对照真实 MDL、指标口径与数据库结果；一次文件加载成功不能当作答案准确。

## 9. Agent 岗位面试知识点

这是常见技术知识点，**不是公开面经**：为什么把指标定义从代码移到外部资料？可以结合本项目说明：代码负责查找和执行，目录记录业务事实及来源，两者的变更节奏不同。还要区分“Pydantic 证明结构合法”和“业务审核证明定义可信”，以及为什么 RAG 检索命中后仍需校验来源与口径。

## 10. 下一阶段的前置条件

先能解释 `文件路径 → load_metric_catalog → metric_catalog → Query → answer`，并理解默认空目录的原因。要建立真实指标知识，需要用户环境中经过核实的 MDL/指标定义、表字段、业务过滤条件和来源；随后才可设计 SQL 构建与校验。规则、SQL 片段和血缘资料积累到需要动态检索时，再引入 RAG。
