# 第 33 课：多表血缘与分析证据

## 1. 解决什么问题

以前“血缘”只能指到日报字段。现在可说明 GMV 来源于已支付订单金额，如何关联商品和活动，以及经过什么筛选到达日报。

## 2. 架构位置

Query 的血缘任务核对 SQL 和实际数据库；Analysis 仍只消费 `QueryEvidence`，不直接查询数据库。

## 3. 本次文件与方法

- `lineage.py`：`describe_lineage()` 解析查询 SQL 和 ETL SQL 的表、列，验证批准映射。
- `commerce_data.py`：`verify_etl()` 重新运行只读 JOIN 并与日报逐行比较。
- `tools/analysis.py`：放纯 Python 的行业贡献和漏斗计算。

## 4. 调用链与数据载体

血缘问句 → `IntentResult(lineage)` → Query → 指标目录 + `KnowledgeBase` + 实际 SQLite 表 → 血缘文本。分析问句则是 Query → `QueryEvidence` → Analysis 工具 → `WorkflowResult.answer`。

## 5. 关键执行过程

以 GMV 为例：`fact_order.pay_amount_cents` 仅计 `paid` → JOIN 访客、商品、活动 → `commerce_daily.pay_amount_cents` → 指标 SQL 求和。若改坏上游金额但不更新日报，`verify_etl()` 会拒绝这条血缘。行业贡献必须加总到整体差额；漏斗恒等式也需对齐。

## 6. 为什么这样设计

**原文要求**血缘与归因。当前实现是字段和转换血缘、数值贡献诊断；没有真实营销实验，不能证明因果。LightRAG 是可选的知识检索方案，本地确定性血缘已经能被单元测试核对，暂不接入图检索服务。

## 7. 测试与限制

最终 47 项离线测试通过，其中包含篡改上游订单导致校验失败，以及血缘文本包含已支付筛选和维表。上游订单由汇总样例合成，血缘只能证明本地加工过程，不证明生产 ETL。

## 8. 相关知识

第十二章评估：血缘正确性要检查来源、转换、过滤和目标字段，不能只看回答是否流畅。

## 9. 面试知识点

区分字段血缘、表血缘、业务口径血缘；解释为何“贡献最大”不等于“导致下降的原因”。这是常见技术知识点。
