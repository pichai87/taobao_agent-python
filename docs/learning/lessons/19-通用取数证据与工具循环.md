# 第 19 课：从第 17 课直接走向通用取数证据

> 已掌握第 17 课即可读本课。第 18 课是已被替换的过渡实现，不需要补学。

## 1. 这课解决什么问题

第 17 课的分析证据固定为“前一天金额、后一天金额”。换成三个日期，就得再写一套字段和调用逻辑。本课把它改为**一组按日期排列的观测值**：一个日期可直接回答取数，两个或更多日期可交给 Analysis 计算变化。Query 先找指标定义，再调用受控取数工具。

例子：问 2010-12-01、02、03 的“交易明细金额”变化，Query 返回三条带日期的金额，Analysis 报告首末变化和相邻日期变化。它仍不能凭总额判断下降原因。

## 2. 在参考项目架构中的位置

- **原文要求**：PDF 第 3、5～7 页描述 Intent 单次生成参数包、Supervisor 分发专家、Query 的 `search_metrics → rule_search → build_sql → odps_query` 推理执行，再交给 Analysis。第 19 页的完整波动归因还要漏斗指标和维度拆解。
- **本次实现的原文子链**：Intent → Supervisor → Query 的 `search_metrics → query_daily_metric` → Analysis。`query_daily_metric` 内部沿用指标审批、固定 SQL 门禁和只读 SQLite；它是当前公开数据的受控替代工具，**不是 ODPS，也不是完整 NL2MDL2SQL**。
- **必要工程补充**：用 `MetricQueryPlan` 限定指标和日期，用 `MetricSeriesEvidence` 验证交接的数据；设置最多 7 个日期、9 轮模型交互和 10 次工具调用。这些数字是当前项目的执行预算，并非 PDF 给出的固定值。

当前只使用一张 LangGraph 图。与第 17 课相比，节点和主要边没有增加；主要变化在 **State 里传递的证据结构**和 Query 节点内部。`next_expert=analysis` 时，仍先经过 Query 取得缺少的证据。

## 3. 相对第 17 课，文件改了什么

| 文件 | 现在做什么 |
| --- | --- |
| `intent_agent.py` | 保留已学过的 `curr/prev`；新增 `dates`，让多日期问法能表示完整列表。`requested_dates()` 统一给 Query 使用。 |
| `query_agent.py` | `MetricQueryPlan` 核对日期；`fetch_metric_series()` 取回完整一组结果；受控工具循环先查指标，再按任务查日期。 |
| `analysis_agent.py` | `MetricSeriesEvidence.values` 保存按日期排列的结果；计算首末和相邻变化，不直接取数。 |
| `workflow.py` | `State.query_evidence` 保存一组观测值，Query 成功后才路由 Analysis。 |
| 测试与评测样例 | 加入三日问题、工具顺序、错误参数和失败不泄露部分金额的验证。 |

第 18 课的“从用户问题匹配两笔金额就直接进入 Analysis”分支已移除；它不属于 PDF 的主要取数路线。`ToolCallingModel` 只是“这个模型支持 `bind_tools()`”的类型说明；CLI 仍只创建**一个**模型对象，Intent 和 Query 共用。

## 4. 调用链和数据怎样流动

```text
用户问题
  → IntentResult: metric_name、curr/prev、dates、intent_type
  → State.intent: 保存校验后的字典
  → Supervisor: State.next_expert = query 或 analysis
  → Query: MetricQueryPlan(metric_name, dates)
     → 模型建议 search_metrics；程序执行并核对指标
     → 模型建议 query_daily_metric；程序核对每个日期后执行
     → SQL Gate + 只读 SQLite → DailyMetricValue 列表
  → State.query_evidence: MetricSeriesEvidence 的字典
  → 若最终专家是 Analysis：验证证据 → 计算变化 → State.answer
  → WorkflowResult.answer 返回主命令
```

单日或多日的**取数**问题在 Query 直接回答；需要计算变化的**分析**问题由 Query 将证据交给 Analysis。`dates` 是 Intent 提出的日期；`MetricQueryPlan` 是 Query 允许执行的任务；`DailyMetricValue` 是一次实际查询结果；`MetricSeriesEvidence` 是交接给 Analysis 的完整集合。不要把这些对象理解成多个 Agent。

## 5. 关键执行和校验位置

1. Intent 的 `dates` 必须是 ISO 日期且不能重复；`curr/prev` 若同时给出，须与列表末尾/开头一致。没有新列表时，老的 `prev/curr` 双日问法仍可运行。
2. Query 拒绝无日期、倒序或超过 7 日期的任务，并核对问题中明确写出的日期不能被 Intent 漏掉；当前数据源也拒绝指定范围、分组及复合任务。这是能力边界，避免假装已经支持原文的维度拆解。
3. 模型拿到 `search_metrics` 和 `query_daily_metric` 两个工具的定义。模型输出的是**工具调用建议**；程序检查工具名、参数、指标、日期、是否重复及先查指标的顺序，再执行。模型不能提交 SQL 或数据库路径。
4. 受控日指标工具仍检查批准的指标，经过固定 SQL 后置门禁并以只读连接查询。工具返回的指标名和日期还要与任务逐项一致。
5. 只有所有日期都成功，Query 才形成 `MetricSeriesEvidence`；任意一次失败都不给 Analysis 半份金额。Analysis 再检查日期递增、同指标、同来源和同单位。

这体现 PDF 的 Harness 思路：模型可提出下一步动作，但执行预算、权限和结果校验在程序一侧。当前循环只覆盖两个工具，尚非原文的完整 ReAct 取数链。

## 6. 设计取舍

只把 `previous_minor/current_minor` 改名为一个列表，能解决字段数量问题，却仍会让 Query 按代码固定调用同一工具。本课同时接上指标查找和日指标查询的两工具循环，更接近 PDF 第 6 页“先找指标，再取数”的过程。以后有可信 SQL 规则与业务表时，才能继续加入 `rule_search`、`build_sql` 和对应查询工具；不能凭 UCI 这三列数据编造淘宝业务表。

当前 `dates` 是对原有 `curr/prev` 的兼容扩展，减少你已学接口的突然变化。等更多任务类型稳定后，可统一 Intent 的时间契约；本课不为未来所有时间问法先搭一个复杂框架。

## 7. 实际运行验证

在项目根目录执行：

```bash
UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -p 'test_*.py' -q
```

目的：运行本地单元测试和主图集成测试，**不发送模型请求**。实际结果：**77 个测试通过，退出码 0**。验证了老双日问法、三日问法、单日与多日取数、工具顺序与错误参数、漏掉明确日期、日期错位以及失败时不返回部分金额。它不证明真实模型能稳定选择正确工具。

还执行了 `uv run --locked --offline taobao-agent --help`（检查入口能启动）和 `uv run --locked --offline python -m json.tool tests/fixtures/intent_golden.json`（检查评测文件格式）；两条均退出码 0。前者不执行查询，后者不评测模型。

还用固定输出的假模型贯穿本机已导入的 UCI SQLite，实际得到：2010-12-01 **58960.79**、12-02 **47748.38**、12-03 **46943.71** 英镑；首末下降 **12017.08 英镑、20.38%**，相邻两段分别下降 **11212.41** 和 **804.67** 英镑。旧双日问法仍得到下降 **11212.41 英镑、19.02%**。这些检查使用了真实本地数据，但模型输出是测试固定值。

你可以用 README 的三日命令在自己的 Plus Key 环境验证真实模型。该命令的目的是检查 Intent 是否提取三个日期、Query 是否完成两工具循环；预期为上面的数值。**本课环境没有 `DASHSCOPE_API_KEY`，未执行在线百炼请求**。一次成功也不能代表各类问法的准确率。无需安装数据库服务或 Navicat。

## 8. 按需学习的相关知识

- **第九章，上下文工程**：Query 只接收当前问题和核准的指标、日期，工具结果回到它自己的消息列表；Analysis 只拿到结构化证据。这是当前的专家上下文边界。
- **第十章，通信协议**：`bind_tools()` 把本地工具定义提供给模型；模型返回调用建议，Python 实际执行。专家之间通过 LangGraph State 交接，不需要 MCP 或 A2A。
- **第十二章，评估**：将 Intent 日期提取、工具选择、参数构造、取数结果和 Analysis 算术分别验证。`tests/fixtures/intent_golden.json` 新增三日问法；在线评测尚未运行，不能把本地 77 个测试说成模型成功率。

## 9. Agent 岗位面试知识点

以下是**常见技术知识点与模拟面试题**，不是公开真实面经：

- 为什么模型已经“注册”工具，程序还要验证再执行？注册只让模型知道接口；实际执行涉及权限、口径和成本，必须有边界。
- 为什么 `next_expert=analysis` 仍先走 Query？它表示最终负责回答的专家，取数是前置任务。
- 为什么证据用日期列表而不是 `prev/current` 两个金额？列表能表示 1～N 个观测值，并由同一契约校验完整性；算术仍可选择基期和末期。

## 10. 下一步前置条件

当前 UCI 导入表只有日期、记录类型和金额，没有行业、访客数、转化率或客单价。它不能复现 PDF 第 19 页的归因诊断树。下一步应先核对可用的公开数据字段与业务口径，取得可验证的分组/漏斗指标，再把规则检索、SQL 构建与门禁串入 Query，逐步接近原文的 NL2MDL2SQL。若数据不具备这些字段，Analysis 必须继续明确说“仅凭总额无法判断原因”。
