# 第 14 课：两日金额变化与 Analysis 节点

## 1. 本课解决什么问题

问题例子：“2010-12-02 交易明细金额为什么比 2010-12-01 下降？”以前 Supervisor 会选 `analysis`，但主图随即结束，`answer` 是空的。本课让 Analysis 真正执行：查询两天金额，计算差额与变化率，并明确指出**这还不能解释下降原因**。

一句话结论：**同一指标的两次可信取数可以证明变化幅度，不能单凭总额证明因果。**

## 2. 在整体架构中的位置

原文把 Analysis Agent 定位为波动归因诊断，示例会继续拆访客数、转化率、客单价等。我们手头的 UCI Online Retail 数据只有交易明细，没有访客或转化率，也没有淘宝补贴和支付状态。本课是达到原文目标前的一项**必要工程补充**：先把有证据的两日总额比较接入 Analysis。完整归因树、行业拆解、Ops、RAG 都尚未实现。

UCI 指标名是“交易明细金额”，不是已支付 GMV。教学模式的 GMV 则来自 6 笔手工合成订单。两种数据不能混称。

## 4. 调用链：参数怎样流动

以示例问题为例：

```text
用户问题
  → Intent：生成 IntentResult(intent_type="attribution", metric_name="交易明细金额",
                            curr=2010-12-02, prev=2010-12-01)
  → State.intent：保存为字典，供后续节点读取
  → Supervisor：写入 State.next_expert="analysis"
  → Analysis：从 State.intent 还原并校验 IntentResult
      → 查已配置的指标定义
      → query_uci_metric(指标, prev, 数据库路径) = 5,896,079 便士
      → query_uci_metric(指标, curr, 数据库路径) = 4,774,838 便士
      → 差额 = 当前 - 基期 = -1,121,241 便士
      → 下降率 = 差额绝对值 ÷ 基期 × 100 = 19.02%
  → State.answer：写入中文回答
  → WorkflowResult.answer：作为主命令 JSON 的 answer 字段返回
```

`IntentResult` 是经过 Pydantic 校验的意图对象；`State.intent` 是 LangGraph 节点之间传递它的字典形式。Analysis 读入后重新校验，所以节点不直接信任任意 State 字典。`WorkflowResult` 只负责把整张图最后的结果给 CLI。这里唯一新用到的 LangGraph 概念，是**条件边落到一个真实节点**：原来 `analysis` 直接到 `END`，现在到 `analysis_node`，再到 `END`。

## 5. 关键代码如何执行

1. 先要求指标名和两个不同的明确日期；指定范围、分组或复合任务暂不执行，避免回答比数据支持的范围更广。
2. 从当前模式的指标目录精确查找指标。没有指标定义时，不能猜表名和字段。
3. 教学模式调用 `query_demo_metric()` 两次；UCI 模式调用 `query_uci_metric()` 两次。每次内部仍经过固定模板 SQL 校验和 SQLite 只读连接。
4. 金额一直用整数“分”或“便士”计算；只有显示时才转为元或英镑。百分比使用 `Decimal`，保留两位小数，减少浮点显示误差。
5. 如果基期为 0，返回“变化率无法计算”。如果任一次查询失败，不输出第一次已拿到的金额，避免把半份结果写成完整比较。
6. 最后给出两天金额、绝对差额、变化率和数据口径。回答明确说总额不足以判断原因。

例如 2010-12-01 为 58960.79 英镑，2010-12-02 为 47748.38 英镑。`(47748.38 - 58960.79) / 58960.79 × 100` 约为 `-19.02%`；回答用“下降 19.02%”表达方向。它**没有**证明是哪类商品、访客或转化环节导致下降。

## 6. 为什么这样设计；还有哪些方案

- **原文要求**：Analysis 面向波动诊断。原文的完整诊断需要多指标和分组数据；本课没有把“两日比较”冒充已完成归因。
- **必要工程补充**：先复用可信指标目录与已验证的查询工具，给 Analysis 一条可核算的输入路径。这样既不重复实现 SQL，也保留同样的门禁。
- **可选方案**：让模型直接根据问题给出下降原因；当前没有相应证据，容易编造。等有访客、转化率、客单价及维度数据时，再加入可验证的拆解与更完整的专家分析。

## 7. 如何运行，以及实际验证结果

在项目根目录执行：

```bash
UV_CACHE_DIR=/private/tmp/taobao-agent-uv-cache uv run --locked --offline python -m unittest discover -s tests -v
```

**目的**：在不消耗 API Key 的情况下验证 Analysis 数值、图路由、单次模型调用、基期为零、缺日期、越界与第二次查询失败的行为，也回归以前的功能。**实际结果**：65 个测试通过，退出码 0。**不能证明**：真实模型一定正确识别新问法，也不能证明任意业务问题都能归因。

本地已有第 13 课数据库时，也用代码中的 Analysis 函数对真实 UCI SQLite 做了实测：基期 58960.79 英镑、当日 47748.38 英镑、下降 11212.41 英镑、下降率 19.02%。该运行没有调用模型；它验证的是现有数据库、指标规则、SQL 门禁、只读查询和比较计算。

若要在你自己的终端检查**完整的在线主流程**，先确保 Plus Key 已在该终端的 `DASHSCOPE_PLUS_API_KEY` 中，然后运行：

```bash
env -u TAOBAO_METRIC_CATALOG_PATH -u TAOBAO_DEMO_DATA TAOBAO_UCI_DB_PATH=data/uci_online_retail/online_retail.sqlite DASHSCOPE_API_KEY="$DASHSCOPE_PLUS_API_KEY" DASHSCOPE_MODEL=qwen-plus uv run taobao-agent '2010-12-02 交易明细金额为什么比 2010-12-01 下降？'
```

**目的**：用一次真实模型调用检查意图和两个日期是否提取正确，再看图是否进入 Analysis。**预期**：`next_expert=analysis`；`answer` 含两天金额、`下降 11212.41 英镑` 和 `变化率 19.02%`。**实际状态**：截至本课编写，这条新问法尚未用用户 Key 在线运行；如果日期识别错误，不能用本地测试宣称在线链路通过。命令不需要 Navicat 或数据库服务，Python 自带 SQLite 即可。

## 8. 本课涉及的关联知识

- **第九章，上下文工程**：Analysis 只读取当前问题的结构化 `intent`、已配置的指标规则和查询结果；没有把整个对话历史塞进提示词。当前不需要额外上下文构建模块。
- **第十章，通信协议**：Supervisor 到 Analysis 是同一 Python 进程内的 LangGraph 节点交接；Analysis 到查询工具是普通函数调用。没有跨进程协议需求，因此不引入 MCP 或 A2A。
- **第十二章，评估**：本课的业务断言检查确切金额和变化率；失败用例检查“不编造比较结果”。这些是单元与本地集成测试，不是在线 Agent 准确率。真实模型还需要更多日期和问法组成的小型评测集。

## 9. 对应的 Agent 岗位面试知识点

常见技术知识点：为什么多 Agent 的每个专家要有清晰的输入、输出和证据边界？本课的答案是，Analysis 接收经过验证的意图，只能基于两次受控查询给出描述性变化，不能越过数据证据宣称因果。另一个知识点是百分比的分母和零基期处理：变化率以**基期**为分母，基期为零时不能做普通百分比计算。这些是本项目的工程例子，不是引用某份真实公开面经。

## 10. 下一课的前置条件

先看一次上述在线主命令的 JSON 输出，确认模型对指标名、`curr` 和 `prev` 的提取。之后可选择一个完整业务能力：例如在 UCI 数据中加入**有来源、有口径的分组拆解**，使 Analysis 从“变化多少”前进到“哪些分组贡献了变化”；若要做原文中的访客/转化率归因，必须先取得这些指标及相应数据。本课结束后先等待你的反馈和确认，再进入下一课。
