# 第 26 课：单一数据源与统一取数链

## 1. 本课解决什么问题

**一句话**：把第 25 课因“旧 UCI 库／增强 UCI 库”形成的两条 Query 和 Analysis 执行路径，收敛为一份合成电商数据、一种查询证据和一个 SQL 执行入口。

此前你看到同一个 Query 节点按数据库类型选择 `fetch_metric_series()` 或 `fetch_aggregate_evidence()`；Analysis 也按两种证据分别处理。虽然图只有一张，学习和维护仍需记两套函数。现在这些分支已退出运行代码。用户只运行 `taobao-agent`，数据只来自当前创建的 `commerce.sqlite`。

**原文要求**：Intent → Supervisor → 专家 Agent；Query 按指标、规则、SQL、取数推进；SQL 在执行前校验；Analysis 用查询证据做波动拆解。**必要工程替代**：我们没有淘宝 ODPS 数据，使用可逐行核算的 SQLite 合成样例。**本课设计选择**：所有问法共用一个 Query 请求／证据契约，没有为单日和分组另外造专家。

## 2. 在整体架构中的位置

```text
用户问题
  → Intent：LLM 生成 IntentResult
  → Supervisor：决定 query 或最终 analysis
  → Query：QueryRequest → 四个受控工具 → SQL Gate → SQLite → QueryEvidence
  → 若需要分析，Analysis：只读 QueryEvidence → Python 计算 → 答案
```

LangGraph 在这里仍只负责 **State**（节点交接的数据）与 **条件边**（决定是否进入 Analysis）。本课没有增加新节点。`State.query_evidence` 是 Query 和 Analysis 的唯一数据交接字段。

## 4. 调用链：参数、State 和返回值怎么流动

以“2026-10-22 百亿补贴 GMV 比 2026-10-21 为什么下降？按行业拆解”为例：

1. Intent 的模型调用输出 `IntentResult`：主意图 `attribution`、指标 `GMV`、两个日期、维度 `行业`。模型提出的是**任务参数**，不是查询结果。
2. Supervisor 把最终专家选为 `analysis`；图先进入 Query 取证据。
3. `request_from_intent()` 生成 `QueryRequest`：两个单日、按行业；GMV 分析还需要 `访客数`、`订单数`，因此把它们纳入同一任务。这里的请求只描述**要查什么**。
4. Query 的 LLM 依次提出 `search_metrics → rule_search → build_sql → execute_query`。Python 每一步核对工具名、指标、日期和维度。`execute_query` 不接受模型给出的原始 SQL。
5. `commerce_data.query_metric()` 在只读 SQLite 入口调用 `validate_metric_query()`。后者对照批准模板、绑定参数和真实字段；通过才执行。
6. Query 收齐 3 个指标 × 2 天 = 6 条 `Observation`，形成 `QueryEvidence`。它检查结果不缺失、不重复、来源一致，才写入 `State.query_evidence`。
7. Analysis 从 State 还原 `QueryEvidence`，不连接数据库。模型只选受限分析视角；金额、变化率、漏斗和行业贡献均由 Python 计算，写入 `State.answer`，最后由 `WorkflowResult.answer` 返回。

单日、多指标范围和分组问题也走第 3～6 步，区别只在 `QueryRequest` 的指标、时间段和维度参数，不再切换执行模块。

## 5. 数据口径与关键计算

CSV 是**编造的教学数据**，不是 UCI，也不是淘宝真实业务。每行有日期、行业、活动类型、访客数、订单数和支付金额（分）。目录只批准三种求和指标：GMV、访客数、订单数；三者都必须筛选 `activity_type=百亿补贴`。额外的“普通活动”一行用于检查筛选是否被遗漏。

| 日期 | 百亿补贴 GMV | 访客数 | 订单数 |
| --- | ---: | ---: | ---: |
| 2026-10-21 | 24000.00 元 | 2400 | 240 |
| 2026-10-22 | 20600.00 元 | 2500 | 206 |

`转化率 = 订单数 ÷ 访客数`，从 10.00% 变为 8.24%；`客单价 = GMV ÷ 订单数`，两天都是 100.00 元。家电 GMV 减少 3400.00 元，服装和食品不变，总下降也为 3400.00 元。漏斗的顺序数值拆解为访客数增加 1000.00 元、转化率减少 4400.00 元、客单价影响 0.00 元；相加恰为净下降 3400.00 元。**拆解的顺序会影响各因子分摊，数值贡献不能证明经营因果。**

## 6. 为什么这样设计；还有什么替代方案

保留 UCI 可以沿用真实交易数据，但它没有访客和补贴字段，无法验证 PDF 的 GMV 漏斗诊断。给 UCI 凭空补访客会混淆真实来源与编造数据。因此本课选择一份完整标记为合成的数据；未来接真实数据时只替换数据适配和已审核指标定义，不增加第二条 Query Agent 主流程。

模型负责理解问题与提出工具调用，程序负责参数批准、SQL Gate、取数和精确计算。这使模型不能靠“自觉”遵守权限，也让错误可定位到 Intent、工具参数、SQL Gate、数据库或 Analysis。当前 SQL 是固定受控模板，尚未实现 PDF 中 WrenAI 的完整 NL2MDL2SQL；下一包再把已有指标知识发展为最小 MDL、规则与 SQL 片段层。

- `PYTHONPYCACHEPREFIX=/private/tmp/taobao-pycache .venv/bin/python -m unittest discover -s tests -v`：**30 个离线测试通过**。覆盖单日、范围、多指标、行业分组、完整 Query → Analysis、口径组合问法、七题固定模型输出、篡改 SQL 与参数拒绝、来源和日期限制；新增“格式错误后成功重试”和“三次格式错误后停止”两项。使用假模型，因此**不能证明真实 Qwen 的工具选择可靠**。
- 真实 `qwen-plus` 七题首轮评测：**5/7**。单日、多指标范围、指标口径、口径＋金额及未知指标题通过；两道 Analysis 题的 Intent、Supervisor 检查均通过，但 Query 工具调用被拒绝，因而没有证据交给 Analysis。失败表现为受控错误回答，并非编造金额。不能把上述离线通过数当作在线通过数。

### 真实失败题的纠错过程

1. **观察**：`gmv_decline_industry`、`three_day_high_low` 未通过；报告显示意图、最终专家、指标、日期和维度均正确，只有答案断言失败。两题都停在 Query，Analysis 没有收到 `QueryEvidence`。首轮报告保存在 `/private/tmp/taobao-eval-unified-first.json`，没有覆盖。
2. **定位**：给受控拒绝答案补上程序自己的错误类别后，仅重跑这两题，结果 **0/2**；答案明确显示“模型提出了无效工具参数”。这说明问题位于 LLM 提出工具调用到 Pydantic 解析的边界，而不是 SQL 执行或分析计算。诊断报告是 `/private/tmp/taobao-eval-unified-diagnostic.json`。日志没有保存 API Key 或模型原文。
3. **修正**：Query 在当前工具调用缺失、重复或格式错误时，最多重试两次，每次只把当前**已批准**任务的参数格式重新告诉模型。模型仍不能修改指标、日期、维度或 SQL；三次失败便停止，不返回部分数据。这里只修复调用格式，不放松 `QueryRequest`、工具参数核对或 SQL Gate。
4. **定向复测**：新增离线测试证明一次格式错误可以恢复、连续三次错误会停止。真实 `qwen-plus` 只重跑两道原失败题，结果 **2/2**；归因题拿到 6 条证据，回答 GMV 从 24000.00 元降到 20600.00 元，行业净降幅 3400.00 元，漏斗数值可核对；三日题正确给出最高与最低日期。报告在 `/private/tmp/taobao-eval-unified-retest.json`。这证明修正后的这两次调用成功，尚不能证明其他问法的稳定性。
5. **完整回归**：再次运行全部七题，真实 `qwen-plus` 结果 **7/7**；七题的意图、路由、指标、日期、维度、答案必含与禁含检查均通过。报告保存在 `/private/tmp/taobao-eval-unified-final.json`，没有覆盖前面三个报告。单次通过只说明该固定题集本次成功，不能推断任意问题均可靠。

在线运行的命令是 `env -u TAOBAO_UCI_DB_PATH -u TAOBAO_DEMO_DATA DASHSCOPE_API_KEY="${DASHSCOPE_PLUS_API_KEY:-$DASHSCOPE_API_KEY}" DASHSCOPE_MODEL=qwen-plus uv run taobao-eval --diagnostic > /private/tmp/taobao-eval-unified-final.json 2> /private/tmp/taobao-eval-unified-final-error.txt`。**目的**：用当前真实模型和唯一数据库重跑七题，并把诊断留在本机；**预期**：JSON 中 `total=7`、`passed=7`；**不能证明**：未知问法、长期模型波动或真实淘宝数据的正确性。Key 只从用户终端环境传入，报告不保存 Key。

**本轮遇到并解决的工程问题**：首次使用空的临时 uv 缓存运行 `uv lock --offline`，因缺少依赖索引而失败；改用正式的 `uv lock` 后成功。首次直接运行系统 Python 的 `compileall`，试图写入受限系统缓存目录而失败；指定 `PYTHONPYCACHEPREFIX` 后编译通过。这两项是环境／缓存问题，不是业务代码通过或失败的证据。旧库 96 项测试中的大多数只验证已移除的 UCI 与教学模式；本课改为 30 项当前主路径测试，**测试数减少不代表质量自动提高**，还需持续扩充业务评测。

## 8. 相关学习知识

- **第九章，上下文工程**：Query 只把已批准的 `QueryRequest` 和当前工具说明传给模型，不把整个数据库或旧数据集塞进提示；工具结果逐轮加入当前 Query 的消息。Analysis 只收到已核实证据。这是本课的上下文边界。
- **第十章，通信与工具**：四个工具通过同一进程的 Python 函数实现 Tool Calling。专家之间由 LangGraph State 传 `QueryEvidence`；这里没有跨服务通信需求，因此不引入 MCP 或 A2A。
- **第十二章，评估**：离线集成测试检查程序契约，Golden Dataset 的在线运行检查真实模型行为；没有 LLM Judge 或外部标准基准。失败先看是哪一层，而不是只看最终答案。

## 9. Agent 岗位面试知识点

以下是常见技术讨论点和模拟面试题，并非公开真实面经：

1. **为什么“一个 Agent 节点”也可能有两套运行路径？** 节点内部仍可按数据源分支。应检查节点调用的函数和证据类型，不能只数图节点。
2. **为什么 Analysis 不直接查数据库？** Query 负责指标口径、SQL 权限和证据完整；Analysis 消费结构化证据，便于独立验证计算，也避免绕过 SQL Gate。
3. **模型 Tool Calling 后为什么还要校验参数？** 工具建议仍可能漏字段、错日期或越权。SQL 执行边界再次校验候选语句和实际表结构。
4. **为什么固定样例 7/7 不等于可靠？** 它只覆盖预先写出的问法；还需要变体、错误输入、模型波动和回归测试。
