# 第 31 课：多表数据与项目结构

## 1. 解决什么问题

以前只有一张日报表，无法解释金额、订单和访客来自哪里。现在保留旧库，另建 `commerce_v2.sqlite`：商品维表、活动维表、每日访客表和订单表经过同一段 ETL SQL 生成日报。

## 2. 架构位置

这是 Query 的数据底座；所有专家仍共用同一个数据库路径。`agents/` 放专家与运行门禁，`tools/` 放可复用的计算和数据工具，`web/` 放接口。不创建 ODPS、DataWorks、前端或 WrenAI 的空壳。

## 3. 本次文件与方法

- `commerce_data.py`：`seed_commerce_db()` 建表、生成合成订单、核对日报；`verify_etl()` 重新计算上游数据。
- `tools/etl.py`：`DAILY_ETL_SELECT` 是经过审查的多表关联和支付状态筛选。
- `examples/commerce_metrics.json`：三项指标的来源版本改为 v2。

## 4. 调用链与数据载体

`commerce_daily.csv` 的 10 行汇总样例 → Python 确定性拆为订单和访客 → SQLite 四张上游表 → ETL SQL → `commerce_daily`。`SeedSummary` 只记录来源、哈希、行数和日期；运行时 `MetricResult` 仍承载查询结果。

## 5. 关键执行过程

每行金额按订单数拆分，余数分配到前几笔订单。另加一笔取消订单，金额 999999 分；ETL 只计 `order_status='paid'`。建库完成前比较整张日报与原始 10 行，不一致就拒绝。目标文件使用排他创建，存在时不覆盖。

## 6. 为什么这样设计

原文要求多层数据来源；本地没有淘宝明细和 ODPS，因此这是**必要工程补充**。订单是从汇总样例反向合成的，不能称作真实独立证据。保留旧库是为了保护历史数据，不是建立两条运行路径；新主流程只读 v2。

## 7. 测试与限制

运行 `PYTHONPYCACHEPREFIX=/private/tmp/taobao-pycache .venv/bin/python -m unittest discover -s tests -p 'test_*.py' -q`：最终 47 项通过。测试核对多表 JOIN、支付汇总、取消订单排除和不覆盖文件；证明本地数据链自洽，不能证明真实淘宝经营数据正确。

## 8. 相关知识

本课属于数据建模与可重复 ETL。数据来源和转换规则必须可追溯；RAG 不能替代数值核算。

## 9. 面试知识点

可解释事实表与维表、聚合表、支付状态过滤，以及“合成明细不能当作独立原始证据”。这是常见技术知识点，不是公开面经原题。
