# 第 4 课：把识别结果交给 Supervisor

先看结果：你问“昨天 GMV 比前天为什么下降？”，程序先认出这是**归因问题**，再决定下一位应该是 **Analysis 专家**。目前只做到“选择”，还没有让专家查数或分析。

## 1. 本阶段解决的问题

上一课有两个命令：一个演示简单问答，一个单独识别意图。它们还没有形成项目主流程。本课让 `taobao-agent` 运行一张主图：**Intent → Supervisor**。`taobao-intent` 留作检查意图的工具，调用同一个识别函数。阶段 4 的代码整合又把旧问答图移出运行代码目录，避免误以为主流程还有一个 `answer` 节点。

## 2. 在整体架构中的位置

```text
用户问题 → Intent 节点：这是什么问题？
         → Supervisor 节点：下一位专家是谁？
         → 输出选择结果；专家执行留到下一阶段
```

原文 PDF 第 3、6 页描述了 Intent、Supervisor、Query / Analysis / Ops / Other 的顺序。原文的 Supervisor 还包括日期注入、语义计划和记忆召回。本课先做最小的专家选择；日期已由 Intent 接收参考日期，计划与记忆等到有真实专家和知识时再加入。

## 3. 修改的文件与关键方法

## 4. 调用链、参数与 State

```text
taobao-agent '昨天 GMV 比前天为什么下降？'
  → main() 创建模型，读取今天的日期
  → run_workflow(question, model, reference_date)
  → Intent 节点调用 run_intent_once()，写入 State.intent
  → Supervisor 节点读取 State.intent，写入 State.next_expert
  → 输出 {"intent": ..., "next_expert": "analysis"}
```

这里的 **State** 仍可理解为图中传递的“小纸条”：起初有 `question`；Intent 写入 `intent`；Supervisor 再写入 `next_expert`。节点只增加自己负责的字段。一次正常请求只调用模型一次，因为 Supervisor 目前用明确的 Python 规则选专家。

## 5. 关键代码怎样执行

`run_intent_once()` 保留上一课的 JSON 校验和有限的 429 降级。主图的第一个节点调用它，所以 `taobao-intent` 与 `taobao-agent` 不会有两套不同的意图提示词。

`select_expert()` 只看主意图：`data_query` 和 `table_meta` 交给 `query`；`attribution` 交给 `analysis`；`other` 交给 `other`。次要意图仍在输出中，但本课还不规划多专家执行。Ops 暂未加入选择，因为当前没有经过验证的 Ops 意图类型。

### 阶段 4 代码整合：旧 `answer` 节点去了哪里？

第 2 课的 `minimal_agent.py` 是**当时的练习程序**：`START → answer → END`，直接请模型回答问题。第 4 课的 `workflow.py` 是**现在的主程序**：`START → intent → supervisor → END`，先识别，再选择专家。两者不是一张图逐步加节点；我们已把练习中有用的能力（创建模型、调用模型、检查 JSON、处理限流）放进当前调用链，旧图本身不再执行。

现在运行代码目录里的关系如下：

```text
pyproject.toml: taobao-agent = taobao_agent.workflow:main
  → workflow.main() 创建 model
  → workflow.run_workflow() 运行唯一主图
      → intent 节点调用 intent_agent.run_intent_once()
      → supervisor 节点调用 supervisor.select_expert()
  → 打印 intent 与 next_expert
```

`taobao-intent` 仍是检查同一个 `run_intent_once()` 的独立命令，方便排查“识别错了”还是“选择错了”；它没有自己的 LangGraph 图。旧 `MinimalState`、`MinimalReply`、`build_graph()` 和 `answer` 节点只在 `docs/learning/archive/` 保存供学习，不再由 `src/taobao_agent/` 导入，也不再被当前测试运行。旧测试中仍与当前程序有关的“缺 Key”和“429 提示”检查，已移到 `tests/test_workflow.py`。

**你看到 `answer` 节点的原因**：读到的是第 2 课的文件，而你终端运行的是 `pyproject.toml` 指向的第 4 课入口。判断程序真正执行哪张图，先看 CLI 入口，再沿函数调用看 `build_workflow()`，不要仅凭文件名推断。

## 6. 为什么这样设计

- **原文要求**：Intent 先识别，Supervisor 再分配专家。
- **必要工程补充**：模型配置只保留一个来源；把意图识别变成可复用函数；主 CLI 指向唯一的工作流。
- **本课的边界**：只选择下一位专家。现在没有专家节点，输出的 `analysis` 表示“应该交给 Analysis”，不代表已经完成归因。
- **另一种做法**：持续保留旧练习图在运行包中，便于回顾，但容易误判当前架构；直接删掉则会丢失阶段 2 的学习材料。本次把旧代码和测试移到学习资料，当前包只保留主图。

代码整合后再次执行同一条本地测试命令：**20 个当前测试通过，退出码 0**。测试数量从 24 变为 20，是因为 6 个只检查旧单节点练习的测试退出当前测试套件，同时将其中 2 个仍适用的边界测试移到主流程测试；它不代表删减了主流程行为。执行 `uv run --locked --offline taobao-agent --help`：退出码 0，主入口可用。使用 `build_workflow(...).get_graph().nodes` 读取编译后的节点，得到 `['__start__', 'intent', 'supervisor', '__end__']`；这能直接证明当前主图没有 `answer` 节点。以上本地命令不发送模型请求，也不证明在线识别对所有问题准确。

## 8. 本课涉及的其他知识

- **LangGraph**：本课只新增“第二个节点读取第一个节点写入的 State”。还没有条件边，因为专家节点尚未实现。
- **第九章，上下文工程**：Supervisor 目前只拿到原问题和校验后的意图，不额外请求 SQL 规则或会话记忆。
- **第十章，通信协议**：这两个节点在同一 Python 进程中，直接传 State；不需要 MCP 或 A2A。
- **第十二章，评估**：单元测试证明映射代码符合预期；真实模型评测才能判断意图是否识别正确。若第一步识别错，Supervisor 即使按规则执行也会选错专家。

## 9. Agent 岗位面试知识点

以下是常见技术知识点，**不是公开面经**。面试若问“为什么分开 Intent 和 Supervisor”，可以结合本项目回答：前者把自然语言变成固定字段，后者依据这些字段选择下一步。分开后可以分别测试“有没有听懂问题”和“有没有选对专家”。
